<CaseStudy.Context>

A primeira fase da pós pedia o MVP de uma plataforma de *feature flags* como serviço: uma API monolítica simples para ligar e desligar funcionalidades em produção sem um novo deploy.

O que interessava não era a API em si, e sim o caminho até ela estar no ar: um ambiente na AWS que qualquer pessoa do grupo conseguisse criar, destruir e recriar igual.

</CaseStudy.Context>

<CaseStudy.Process>

<CaseStudy.Step title="A rede primeiro">
Uma VPC com duas sub-redes. A aplicação fica na sub-rede **pública**, em uma EC2 `t3.micro`, acessível pelo Internet Gateway na porta 5000. O banco RDS PostgreSQL fica na sub-rede **privada**, sem acesso público.
</CaseStudy.Step>

<CaseStudy.Step title="Segurança em camadas">
O security group do banco libera a porta 5432 <Mark>apenas para o security group da aplicação</Mark>. O SSH da EC2 é restrito aos IPs do grupo. As credenciais do banco vêm de variáveis de ambiente, nunca do código.
</CaseStudy.Step>

<Terminal title="terraform/" lines={["main.tf          network.tf", "ec2.tf           rds.tf", "iam.tf           security_groups.tf", "variables.tf     outputs.tf", "", "$ terraform apply"]} />

<CaseStudy.Step title="O mesmo ambiente na máquina local">
Um Dockerfile e um Docker Compose sobem a aplicação e o banco localmente, para desenvolver sem depender da nuvem.
</CaseStudy.Step>

<CaseStudy.Step title="Medir o que se construiu">
O projeto foi avaliado contra os 12 fatores e teve o custo estimado na calculadora da AWS antes de ser provisionado.
</CaseStudy.Step>

</CaseStudy.Process>
