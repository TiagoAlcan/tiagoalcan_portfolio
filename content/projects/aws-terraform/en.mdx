<CaseStudy.Context>

The first phase of the program asked for the MVP of a feature-flags-as-a-service platform: a simple monolithic API to switch features on and off in production without a new deploy.

The interesting part was not the API itself but the path to getting it live: an AWS environment anyone in the group could create, destroy and recreate identically.

</CaseStudy.Context>

<CaseStudy.Process>

<CaseStudy.Step title="Network first">
One VPC with two subnets. The application sits in the **public** subnet, on a `t3.micro` EC2 instance reachable through the Internet Gateway on port 5000. The RDS PostgreSQL database sits in the **private** subnet, with no public access.
</CaseStudy.Step>

<CaseStudy.Step title="Security in layers">
The database security group opens port 5432 <Mark>only to the application's security group</Mark>. SSH to the instance is restricted to the group's IPs. Database credentials come from environment variables, never from code.
</CaseStudy.Step>

<Terminal title="terraform/" lines={["main.tf          network.tf", "ec2.tf           rds.tf", "iam.tf           security_groups.tf", "variables.tf     outputs.tf", "", "$ terraform apply"]} />

<CaseStudy.Step title="The same environment on a laptop">
A Dockerfile and a Docker Compose file bring the application and the database up locally, so development does not depend on the cloud.
</CaseStudy.Step>

<CaseStudy.Step title="Measure what was built">
The project was assessed against the twelve factors and had its cost estimated in the AWS calculator before anything was provisioned.
</CaseStudy.Step>

</CaseStudy.Process>
